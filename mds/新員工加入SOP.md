# 新員工加入系統 SOP

> 新員工要能完整使用系統，需開通**兩道門**。少一道就會卡：登不進、或登進去資料讀不到。
> 以下假設新員工信箱為 `xxx@gmail.com`，用你的 owner 帳號操作。
>
> **2026-07-30 起系統與 Google 行事曆完全分家**：登入改成**信箱＋密碼**、課表全在系統資料庫裡。
> 原本的「門 1 Google 登入許可」與「門 3 行事曆共用」都取消了。

---

## 📋 快速清單（照著打勾，約 10 分鐘）

**A. 建帳號** — https://console.firebase.google.com/project/hobe-494909/authentication/users

- [ ] 1. 按「**新增使用者**」→ 填 `xxx@gmail.com` ＋ 隨便一組暫時密碼 → 新增
- [ ] 2. 在剛建好那筆的右邊 **⋮ → 重設密碼** → 把連結／信給新員工，**讓他自己點連結設密碼**
      ⚠️ 這步不能跳，跳了他會「登得進去但每一頁空白」

**B. 加白名單** — 本專案 [`firestore.rules`](../firestore.rules)

- [ ] 3. 在 email 清單**加一行** `'xxx@gmail.com'`（前一行結尾要有逗號）
      ⚠️ 是**加一行**，不是改寫現有的行。覆蓋掉誰，那個人就進不去了
- [ ] 4. 打開 https://console.firebase.google.com/project/hobe-494909/firestore/rules
- [ ] 5. 在編輯器裡 `Cmd+A` 全選 → 貼上整份新規則 → 右上角按「**發布**」
      💡 貼錯不用怕：語法有問題 Console 會標紅字、發布鈕按不下去。發布後也有版本記錄可還原

**C. 驗收**

- [ ] 6. **你自己**重新整理系統 → 學生／課程頁還看得到資料（確認沒誤傷自己人）
- [ ] 7. 新員工登入 https://jyunz47.github.io/hobe-system/ → 看得到學生／課程 = 完成
- [ ] 8. 把 `firestore.rules` 的改動 commit 留底

---

## 📋 離職清單（兩邊都要做）

- [ ] 1. `firestore.rules` 把他那行**刪掉** → Console 貼上 → **發布**
- [ ] 2. Authentication → 找到他那筆 → **⋮ → 停用帳戶**（或刪除）
      💡 不確定會不會回來就選**停用**：一鍵可復原。刪除的話回鍋要重走整份 A+B
- [ ] 3. commit 留底

**刪帳號不會動到資料**：系統沒有把 UID 或信箱寫進任何一筆資料（點名、成績、補課、登記簿都不記「誰建的」），所以離職者經手的資料全部留著、不會出現壞掉的參照。

# 詳細說明

## 門 1：建帳號並設密碼（Firebase Authentication）

不開 → 登入頁按登入會說「信箱或密碼不對」。

1. 打開 https://console.firebase.google.com/project/hobe-494909/authentication/users
2. 「**新增使用者**」→ 填 `xxx@gmail.com` ＋ 一組暫時密碼 → 新增
3. ⚠️ **一定要接著做**：在那筆使用者右邊 **⋮ → 重設密碼**，把連結／信交給新員工，讓他**自己點連結設定密碼**
   - 為什麼不能跳過：Console 直接建的帳號 `email_verified` 是 **false**，會被門 2 的規則擋在外面（登得進去但看不到任何資料）。走完重設密碼的信才會變 true
4. 新員工到登入頁填信箱＋密碼即可（也可以自己在登入頁按「第一次登入／忘記密碼？寄設定密碼信」）

## 門 2：資料庫白名單（Firestore）

不開 → 能登入，但學生／課程／補課資料全讀不到，跳「此帳號未獲授權」。

1. 編輯本專案 [`firestore.rules`](../firestore.rules)，在 email 白名單**加一行** `xxx@gmail.com`（注意逗號）
   - ⚠️ 是**加一行**，不是改寫現有的行。名單上每個信箱＝一個還在用系統的人，不小心覆蓋掉誰，那個人下次登入就是「登得進去但每一頁空白」
2. 打開 https://console.firebase.google.com/project/hobe-494909/firestore/rules
3. 把整份規則貼上 → 按「**發布**」
4. （順手）把 `firestore.rules` 的改動 commit 留底

**要不要用「規則測試區」（Rules Playground）？** 只是加／刪一個信箱的話，用真人測更準（清單的第 6、7 步）。改動規則**邏輯**時才值得開 Playground。想確認白名單本身有沒有關緊，見下方〈定期健檢〉。

## 門 3（規劃中，功能還沒做）：練習課考卷 Drive 資料夾

> **狀態（2026-07-03）**：練習課「考卷檔案上傳」還在設計階段（方案見 [`進展紀錄.md`](進展紀錄.md) 2026-07-03），這道門**現在不用做**，等功能上線後把本段填成具體步驟。

規劃中的方案是「上傳進專用資料夾 → 檔案設連結可檢視 → 連結存資料庫」，對新員工的影響預計是：

- **只看/列印考卷**的員工：**不用開任何門**（點系統裡的連結就能看）
- **要上傳考卷**的員工：需把考卷專用 Drive 資料夾共用給 `xxx@gmail.com`（權限「編輯者」），讓他傳的檔案進同一個資料夾

⚠️ 功能上線時記得回來把這段改成正式步驟、並更新上方清單。

## 定期健檢：確認白名單真的關得住

規則頁下方的「**規則測試區**」可以模擬「某個帳號來讀資料」，不用真的建帳號。

1. 打開 https://console.firebase.google.com/project/hobe-494909/firestore/rules → 展開下方「**規則測試區**」
2. 設定：類型 **get**、位置 `/sharedData/main`、打開「**已驗證**」、供應商 Google、Firebase UID 隨便填
3. **測試一：陌生人要被擋** → 電子郵件填一個不在名單上的（例：`stranger@gmail.com`）→ 執行 → 應該顯示 **拒絕**
4. **測試二：自己人要放行** → 電子郵件改成白名單上的信箱、且 `email_verified` 設為 **true** → 執行 → 應該顯示 **允許**
5. **測試三（重要）**：白名單信箱但 `email_verified` 設 **false** → 執行 → 應該顯示 **拒絕**（這就是門 1 第 2 步不能跳的原因）

三個結果都符合 = 白名單關得住。

## 常見卡點

- **登得進去但每一頁都空、跳「此帳號未獲授權」**：門 2 白名單沒加，或門 1 只建了帳號沒走「重設密碼」的信（`email_verified` 還是 false）。
- **「Firebase 尚未啟用電子郵件/密碼登入方式」**：到 Authentication → 登入方式 把「電子郵件/密碼」啟用。
- **診斷**：系統頁面 F12 → Console 輸入 `firebase.auth().currentUser`，看 `email` 對不對、`emailVerified` 是不是 `true`。

## 帳號管理備註

- **登入方式只留「電子郵件/密碼」**：Authentication → 登入方式裡，Google 與匿名都已停用（2026-07-30）。匿名要**保持停用**——系統沒用到，開著等於多一道沒必要的門。
- **真正的防線只有一條**：Firebase 的網頁設定（API key 那些）是公開資訊，前端一定讀得到，不是祕密。擋住外人的是 [`firestore.rules`](../firestore.rules) 裡的白名單。所以那份名單＝誰能看到全補習班的資料，加人前想清楚。
