## driveData.studentList（學生主清單）

每位學生一個物件，欄位如下（2026-06-01 起）：

| 欄位 | 型別 | 預設 | 說明 |
|---|---|---|---|
| `id` | number | 必填 | `Date.now()` 產生，唯一識別 |
| `name` | string | 必填 | 學生姓名 |
| `grade` | string | 必填 | 國小/國一/國二/國三/高一/高二/高三/大學（見 `GRADES`） |
| `createdAt` | ISO string | 必填 | 建檔時間 |
| ~~`courses`~~ | string[] | — | **已完全退場（2026-07-30）**。2026-06-12 起由 enrollments 取代，cutover 重建後全系統不再有這欄；建檔不寫、學生視窗不再顯示「課程（舊紀錄）」 |
| `school` | string | `''` | 學校名稱（消歧用） |
| `birthYear` | number\|null | `null` | 西元出生年 |
| `parentPhone` | string | `''` | 家長電話（消歧用） |
| `status` | string | `'在學'` | 學生狀態：在學/暫停/離開/畢業 |
| `statusChangedAt` | ISO string | 建檔時間 | 上次 status 變更時間 |
| `statusNote` | string | `''` | status 變更備註（為什麼畢業/離開/暫停） |

### Fallback 規則

2026-05-29 前建立的學生**沒有後 6 個新欄位**，讀取時用以下 fallback：

```js
const status = s.status || '在學';
const school = s.school || '';
const parentPhone = s.parentPhone || '';
const birthYear = s.birthYear ?? null;
const statusNote = s.statusNote || '';
const statusChangedAt = s.statusChangedAt || s.createdAt;
```

新欄位**不批次回填**——使用者透過編輯介面慢慢補。已建檔的舊學生在學生卡會出現「📝 待補資料」chip（school 與 parentPhone 都空才會跳）。

### status 列舉值

| 值 | 意義 | 主清單顯示 | 何時用 |
|---|---|---|---|
| `在學` | 目前上課中 | ✓ 在學分頁 | 預設 |
| `暫停` | 暫時不上但會回來 | 歷屆分頁 → 暫停區 | 短期休息 |
| `離開` | 退費/沒說明 | 歷屆分頁 → 離開區 | 中途不繼續 |
| `畢業` | 正向結束 | 歷屆分頁 → 畢業區 | 完整結業 |

狀態間可互轉（含歷屆→在學 = 復學）。`statusChangedAt` 只記最新一次變更時間，**沒有完整 audit log**（如需歷史時間軸，未來階段再加）。

### 同名同年級規則（2026-06-01 起）

`addStudent` 與 `saveStudentEdit` 都會檢查：若要產生同名同年級學生，**所有同名者（含本人）必須至少有一個辨識欄位（school 或 parentPhone）已填**。沒填會被擋下。

> ⚠️ 這個檢查是**逐字比對 `name`**。若把年級括號塞進名字欄（如「（國小）子晴」vs「子晴」），兩者字串不同 → 不被視為同名 → 警告失效、重複建檔擋不下來。括號年級的正確位置是 **Calendar 備註**（掃描時 `parseScanName` 會拆成 name + gradeHint），**不是名字欄**。舊版掃描曾把括號寫進名字，造成同一人重複，需用硬刪除清理。

### 硬刪除（2026-06-13 起）

學生編輯面板「危險區」可**永久刪除**學生（`confirmDeleteStudent`，需打對姓名）：

- 從 `studentList` 移除該學生
- 連動 `saveEnrollments` 移除**該 studentId 的所有 enrollments**（不分期別）
- `makeupScheduled` 以名字字串記缺席者、**無 studentId 連結**，不在此清理（避免同名誤刪；屬 Calendar 衍生歷史）
- 不碰 Google Calendar
- 與軟刪除（`status` 改歷屆）並存：正常畢業/離開走軟刪除，硬刪除只給清測試帳號／重複資料用

### 不存在 studentList 的東西

- **enrollment（課程歸屬）**：2026-06-12 起抽到 `driveData.enrollments`（見下方章節），是「學生 × 課程」的事實來源；`s.courses` 降為舊欄位
- **出席/請假紀錄**：請假/曠課以 Calendar 事件為事實來源；出席（點名）2026-06-19 起獨立成「按期別分文件」（見下方章節），**不存 studentList、不存 driveData**
- **成績**：2026-06-19 起獨立成「按期別分文件」（見下方章節）

## driveData.enrollments（修課登記簿，2026-06-12 起）

每筆 = 一條「誰、修什麼課、哪個期別、什麼價」的紀錄，是學生 × 課程歸屬的**事實來源**（Calendar 備註降為參考資訊）。

| 欄位 | 型別 | 預設 | 說明 |
|---|---|---|---|
| `id` | number | 必填 | 單調遞增計數器（同 studentList 慣例） |
| `studentId` | number | 必填 | 連 `studentList.id`，同名問題在這層終結 |
| `courseTitle` | string | 必填 | 對應 Calendar 事件課名（`origTitle`） |
| `periodId` | string | 必填 | **帶學年**的期別 id，格式 `'2025-sem2'`（學年-期別），跨學年可查歷史 |
| `price` | number\|null | `null` | 每堂單價。`null` = 用價目表預設；數字 = 個人覆蓋（優惠價）。`0` 是合法價格（免費） |
| `startDate` | ISO\|null | `null` | 第一堂日期（**含當日**）。`null` = 期初就上；插班生才填 |
| `endDate` | ISO\|null | `null` | 最後一堂日期（**含當日**）。`null` = 上到期末；中途退出才填（學費結算時據此裁切堂數） |
| `note` | string | `''` | 備註 |
| `createdAt` | ISO string | 必填 | 建立時間 |

### 寫入路徑

- **學生編輯面板**：加課/退課/改價，按「儲存」才整批寫回（暫存 `_editEnrollments`，取消即丟棄）
- 註：批次入口「課表對帳」（`ensureEnrollments`）已於 2026-07-29 第 4 刀移除；一次性轉換 `migrateCoursesToEnrollments` 已於 2026-07-30 重建完成後移除（雲端殘留的 `enrollmentsMigratedAt` marker 不再被讀取）

### 修課起訖（`startDate` / `endDate`，2026-07-27 起真正生效）

期中人數變動（插班／中途退出）用這組欄位表達，**不是刪掉 enrollment**——刪掉會連過去的堂數與自訂單價一起消失，回頭看舊課堂名冊也少人。

- **語意**：兩端都**含當日**。`enrollmentActiveOn(en, day)` 是唯一判斷點（`enrollment.js`）
- **UI 層講法相反**：畫面一律用「從 X 起加入／從 X 起不上」，`從 X 起不上` 存成 `endDate = X 的前一天`。換算只在 `courses.js` 的 `sysDate*` 做，資料層只認含當日
- **誰吃這組欄位**：`eventRoster` / `eventRosterWithId`（依課堂 `startDt` 裁切）、`courseOccurrencesInRange`（有人設起訖時逐日算名冊，沒人設走單一名冊快取＝成本同舊版）
- **fallback 順序要點**：行事曆課的「查無登記 → 退回備註名單」判斷必須在日期裁切**之前**，否則「當天沒人」會誤退回備註名單
- **寫入路徑**：課程管理 → 點課程 → 名單 → 每位學生的 📅（`sysDateEditOpen`）。學生視窗的修課 tag 唯讀顯示
- **與課名分段連動**：存完起訖，`sysOfferNamePhase()` 算那天的建議課名，跟現行課名不同才問一次要不要一起改（寫進 `courses.namePhases`）。課名顯示一律走 `courseNameOn(co, 日期)`——課堂卡/卡片標題/學生視窗都是，**不要再直接讀 `co.name`**

### 單價解析順序（`effectivePrice`）

個人覆蓋（`en.price`）→ 價目表預設（`coursePrices`）→ 都沒有 = `null`（未定價，UI 紅字提示）

## driveData.makeupScheduled（補課排程）

每筆＝**一場**已排定的補課／調課。**2026-08-05 起一堂請假可以有多筆**（三人同一堂請假，可以各排各的時段），在那之前是「一堂請假一筆」，`originalId` 當唯一鍵。

| 欄位 | 型別 | 說明 |
|---|---|---|
| `id` | string | **這一場自己的身分**（`mk_<base36 時間>_<亂數>`）。2026-08-05 新增；舊紀錄讀進來時自動補成 `id = originalId`（`normalizeMakeupRec`），不改寫 Firestore 原文 |
| `kind` | `'join'`\|undefined | **併班補課**（2026-08-06 第 2 刀）：`'join'`＝這幾個人直接進另一堂既有的課一起上，**不另開場次**；沒有這欄＝一般補課（自己一場） |
| `hostOccId` | string | 只有 `kind==='join'` 才有：**併進哪一堂**的 occId（`sys:<課程id>:<日期>:<時段序>`） |
| `hostTitle` | string | 只有 `kind==='join'` 才有：主課課名快照（給清單/課卡顯示用，主課改名不回溯） |
| `originalId` | string | 來源請假／調課課堂的 occId（**不再唯一**，同一個值可以有好幾筆） |
| `origTitle` | string | 原課程名稱 |
| `originalDate` | ISO string | 原請假/調課時間 |
| `scheduledDate` | ISO string | 補課時段起點（併班＝照抄主課的開始時間） |
| `scheduledEnd` | ISO string | 補課時段終點（併班＝照抄主課的結束時間） |
| `room` | string | 補課教室（併班＝照抄主課的教室） |
| `calEventId` | string\|null | 補課 Calendar 事件 ID（**2026-07-17 第 3 刀起新紀錄一律 `null`**——不再建 Calendar 事件，主頁場次由展開器從本紀錄直接長出；舊紀錄取消安排時仍會刪對應事件） |
| `absentStudents` | string[] | **這一場補誰**的名字（不是整堂的請假名單）。多筆時各自帶自己那份 |
| `calName` | string | 類別標籤（補課／調課） |

> ⚠️ 併班的 `scheduledDate`／`scheduledEnd`／`room` 刻意**照抄主課填滿**，不留空。這樣待補課清單、學生統計、欠課消帳、「已完成」判斷全部沿用一般補課那套邏輯，不必到處特判 `kind`。主課之後被拖去改時間時**這份快照不會跟著動**（已知取捨，第 3 刀再看要不要追）。

### 讀寫入口（別繞過）

- `getMakeupsFor(occId)` → 這堂請假排了哪幾場（依時間排序）。**舊的 `findMakeupScheduledById` 已刪除**——它回傳單筆，留著會讓呼叫端安靜地只看到第一場
- `findMakeupRec(recId)` → 依場次自己的 id 找那一筆（拖曳改時段、取消單場）
- `rebuildMakeupMatchMap()` → 從 `driveData.makeupScheduled` 重建 `makeupMatchMap`（occId → 場次陣列）。**任何寫入之後都要呼叫**，否則畫面讀到的是舊快取
- `mkPendingNames(e)` / `mkPendingCount(e)` → 這堂還沒排補課的人（扣掉已排的、扣掉決定不補課的）。老師請假沒有個別名單 → 用「排了沒」算，回 0 或 1
- `mkStatusOf(e,now)` → `pending`／`scheduled`／`completed`／`skipped`。**只排了一部分人仍是 `pending`**
- `makeupForStudent(e,name)` → 這位學生對到的那一場（只認名單含他的）。**學費／統計要用這支**，拿整堂的第一場當每個人的答案會讓還沒排的人被算成已補
- `joinRecsOn(hostOccId)` / `joinRosterOn(hostOccId)` / `joinCountOn(hostOccId)` → 這堂主課今天多了哪些併班補課生（第二支回傳 `{studentId,name,join:true,fromTitle,recId}`，形狀對齊 `eventRosterWithId`）
- `mkJoinCandidates(ev, avail, students)` → 那天有哪些課可以併，回 `{occ, sameSubject, sameGrade, sameTeacher, exact}`。**`exact`＝三者全中；UI 只列 `exact`，差一項就不列**（2026-08-10 老闆定，沒有「攤開看全部」的路。三個 flag 仍分開回傳，之後若要放寬門檻不必重寫比對）
  - **年級沒有欄位**：`courses` 本體沒有 grade（「高二數學班」是自動命名從名單長出來的字），所以 `mkGradeSet(occ)` **現算**那堂在籍學生的 `studentList.grade` 集合，兩邊交集到就算同年級
  - **老師比 id 不比名字**：`mkSameTeacher()` 兩邊都是系統課時比 `teacherIds`（老師改名也對得上），有一邊是舊行事曆快照才退回比名字
  - **算不出來時寬鬆放行**：某一邊沒人填年級／查不到老師 → 該項不當作「不合」（舊資料常缺，硬擋會讓功能整個沒得用）

### 課堂 id 的影響

`expandMakeupForRange` 長出來的補課場次，課堂 id 是 `mk:<rec.id>`（以前是 `mk:<originalId>`）。同一堂請假排兩場才不會撞成一堂。課堂物件另帶 `makeupRecId`（那一場自己的 id，拖曳改時段用）與 `makeupOriginalId`（來源課堂，反查母課程用）。

**併班補課（`kind:'join'`）不長自己的課堂**——`expandMakeupForRange` 直接跳過它，那幾個人改成疊進主課的名冊。疊的位置在 `enrollment.js` 的 `eventRoster` / `eventRosterWithId`（不是展開器），因為系統課的名冊本來就從登記簿現算、不看課堂物件的 `students`；疊在那一層才會一路長到點名、成績、日曆側欄。

⚠️ **補課生刻意不進 `e.students`**（展開器的在籍名冊）。請假面板的學生 chips 讀的就是那一份——補課生要是能在主課被標請假，會寫出一筆「主課的請假紀錄」而長出不存在的欠課。同理，點名面板不給補課生「曠」鈕（沒來就去待補課清單取消那場安排，人自動回到待安排）。

### 為什麼 `absentStudents` 還是字串陣列？

Calendar 備註本身是字串，沒有 student id 概念。要 id 化的話，得在解析時做名字 → id 的對應——而同名問題會在這層爆。enrollment 資料層 2026-06-12 已建立，等「課程卡改讀 enrollment」「掃描轉對帳」完成後這裡才能徹底 id 化。

目前的同名 workaround：在 Calendar 備註寫「（國小）子晴」，parseScanName 會拆出 name + gradeHint。但仍限於配對掃描，stats 計算（`getStudentStats`）只用名字字串比對。

## 系統自有課表（2026-07-04 老闆整包拍板；2026-07-30 已上線並完成重建）

> **這是什麼**：開發路線 ①「系統擁有課表」的 schema。設計原則＝**旋鈕不是箱子**：不先選類別，填自由欄位（誰/科目/老師/排法/教室/費用），系統自動判類型、自動命名（可手改）。**全部不寫回 Google Calendar**，系統自己是唯一真相。
> **生效時機**：✅ 已生效——2026-07-16 清空、2026-07-30 老闆把真實暑期課表建完，系統自有課表從此是唯一真相。清空工具已於同日移除。

### driveData.courses（課程，每門一筆）

| 欄位 | 型別 | 預設 | 說明 |
|---|---|---|---|
| `id` | number | 必填 | 穩定識別（`Date.now()` 慣例）。**課程身分＝id，不再拿課名當 join key** |
| `name` | string | 自動命名 | 依內容自動長：1人「(學生)(科目)家教」、2人「(學生)、(學生)(科目)班」、3+「(年級)(科目)班」、試聽「(學生)(科目)試聽」；**可手改**。＝建課當下的名字；`nameAuto=true` 時它只是 fallback（見下） |
| `nameAuto` | boolean | 自動 | **滾動命名開關**（2026-08-03 起）：存檔時課名欄留空＝`true`（交給自動命名）、有手打＝`false`。`true` 時 `courseNameOn(co,day)` **逐日現算**（拿那天在籍的名單重跑命名規則），名單一變課名跟著變；`false` 時永遠回 `name`。舊資料沒這欄 → `courseNameIsAuto(co)` 回推：現在的名字若等於自動命名算得出來的（用全部登記或今天在籍的名單各算一次），就當它是自動的（2026-08-03 老闆選「舊課也滾」，判斷刻意寬鬆）。優先序：`namePhases` > 滾動命名 > `name` |
| `namePhases` | array | `[]` | **課名分段**（2026-07-29 起）：`[{from:'YYYY-MM-DD', name}]`，「從某日起改叫別的」，**優先序最高**（蓋過滾動命名）。某天的課名＝`from<=該天` 的最後一段，沒有就往下走 `nameAuto` 的滾動命名、再沒有才回 `name`。名單期中變動（見 enrollments 的修課起訖）時課名跟著變用的。判斷點＝`courses.js` 的 `courseNameOn(co, day)`；建議名字＝`courseSuggestNameOn(co, day)`（拿那天在籍的名單重跑自動命名，**人數會重判課型**好長出「家教/班/團班」，走的是與課堂同一套滾動判型，但只影響字，課程本體 `type`/`teacherRate` 不動；`day=null`＝不裁切用全部登記；**那天沒人在籍回 `''`**）。這支同時是滾動命名的引擎（`courseNameOn` 在 `nameAuto` 時呼叫它） |
| `type` | string | 自動 | 自動長出的標籤：`一對一`/`一對二`/`團班`/`練習課`/`試聽`（不是限制，任何組合合法）。⚠️ **課堂的課型不讀這欄**（見 `typePinned` 的滾動判型）；這欄的角色剩兩個：**費率單位**（`cfRateUnit`）與**滾動判型的 fallback**（練習課/試聽/鎖定/那天 0 人）。存檔時由 `cfType()` 依「全部登記（含已退出）」重算 |

## 點名 / 成績 / 作業（按期別分文件，2026-06-19 起，尚未實作）

> **為什麼不放 driveData**：50 生 × 每週 5 堂 × 40 週 ≈ 1 萬筆點名/年，連同成績、作業塞單一 `driveData` 文件會在一學年內撐爆 Firestore **1MB 單文件上限**。改成**每資料類型 × 每期別各一份文件**（`attendance_2025-sem2` 等），用到才載入：單份有界（每學期約 400KB）、契合現有「整包載入」模型、且 period-scoped 天然支援「學年封存」🔴 需求。
> **periodId 格式**：同 enrollment 的帶學年期別 id（`'2025-sem2'`）。

### attendance_&lt;periodId&gt;（點名）

| 欄位 | 型別 | 說明 |
|---|---|---|
| `eventId` | string | Calendar 事件 instance ID（哪一堂） |
| `date` | ISO string | 上課日（查詢/封存用，免去解析 eventId） |
| `studentId` | number | 連 `studentList.id`，同名問題在此終結 |
| `status` | `'到'` | 有來＝出席（含遲到）。一筆紀錄＝出席一堂 |
| `lateMin` | number | 遲到分鐘數；`0`＝準時、`>0`＝遲到 N 分（**仍算出席、仍算一堂**） |
| `markedAt` | ISO string | 點名時間 |

- **狀態模型（2026-06-19 改）**：實務上「沒按到」的人多半是**遲到**（要記分鐘），真正整堂沒來很罕見、且那就是**曠課**。所以 attendance 只記出席（`status` 一律 `'到'`，`lateMin` 區分準時/遲到），**不再有 `'未到'`**——沒來一律走既有曠課流程（標記請假 → 時機「已開始·曠課」→ 寫回 Calendar 標題 `【X曠課】`）。曠課以 Calendar 為事實來源，不在 attendance 重複記，避免兩套打架。
- **學費堂數來源**：該生該期 attendance 紀錄數（都算出席，含遲到）。取代「排定數 − 不補課的請假/曠課」推算。
- **試聽課不點名**：試聽不算堂數、不結學費，不進點名面板。
- **UI**：今日課程卡內嵌點名面板——「全部到」一鍵、每生「到／遲到（選分鐘 5/10/15/20/30 或自訂）」、罕見沒來按「曠」跳曠課流程；請假/曠課的學生自動帶入鎖定。

|---|---|---|
| `eventId` | string | 哪一堂 |
| `studentId` | number | 連 `studentList.id` |
| `label` | string | 標籤（如「課前考」「第二份考卷」） |

## sharedData/activity（動態與待辦，2026-08-03 起）

**獨立文件**，不在 `sharedData/main` 裡，也不進 `driveData`。理由有二：

1. 事件流只增不減、會一直長大，混進 `main` 會把每次 `scheduleDriveSave` 的寫入量拖大，也更快撞到 Firestore **單文件 1MB** 上限
2. `main` 的存法是「整包 `set({merge:true})` 覆蓋」，多人同時操作會互蓋；動態／待辦要能多人同時寫

`firestore.rules` **不用改** —— 現有白名單 `match /sharedData/{docId}` 已涵蓋這份文件。

```js
{
  events: [ /* 系統自動記的事件，只增不改 */ ],
  todos:  [ /* 員工自己寫的待辦 */ ],
}
```

### events[]（系統動態）

| 欄位 | 型別 | 說明 |
|---|---|---|
| `id` | string | `時間戳-亂數`，只求唯一 |
| `ts` | string | ISO 時間 |
| `by` | string | 操作者登入信箱 |
| `byName` | string | 顯示名（`STAFF_NAMES` 對照表，查無就取信箱 @ 前段） |
| `kind` | string | `absence` / `makeup` / `roster` / `course` / `student` |
| `text` | string | 主句，例：`標記 小明 請假` |
| `target` | string | 對象，例：`8/5（二）17:30 大教室 國一數學` |
| `detail` | string | 補充，例：`課前 1 小時內`（可為空字串） |

**寫入一律 `FieldValue.arrayUnion`**：原子附加，兩個人同一秒各記一筆不會互相蓋掉。寫入失敗只 `console.warn`，**絕不打斷主流程**——動態少記一行，比請假標不成好。

**保留 `ACT_KEEP_DAYS` 天**（預設 60）。載入時把過期的挑出來，用 `FieldValue.arrayRemove` 刪（一次最多 200 筆，剩的下次載入再清）。**刻意不用「整份覆寫成裁切後的陣列」**——覆寫會把別人同一秒 `arrayUnion` 進來的事件洗掉。

⚠️ **只記從 2026-08-03 上線起發生的事**，之前的資料補不回來（沒有可回溯的來源）。

### todos[]（共用待辦）

| 欄位 | 型別 | 說明 |
|---|---|---|
| `id` | string | 同上 |
| `text` | string | 待辦內容 |
| `by` / `byName` | string | 誰寫的 |
| `createdAt` | string | ISO |
| `claimedBy` / `claimedName` | string \| null | 誰認領（null＝還沒人接） |
| `claimedAt` | string \| null | 認領時間 |
| `status` | string | `'open'` / `'doing'` / `'waiting'`（2026-08-03 起） |
| `progress` | array | 進度串，見下（2026-08-03 起） |
| `done` | boolean | 完成與否 |
| `doneBy` / `doneName` / `doneAt` | string \| null | 誰在何時完成 |

#### 狀態（`status`）與進度串（`progress`）

老闆 2026-08-03 定的「接力」模型：一則待辦在完成前會經手多人，下一個人要知道前面做到哪。

**完成刻意不塞進 `status`**，仍用既有的 `done:true` 表示——這樣「取消完成」才回得到原本那一段。畫面上的四段（待處理／處理中／等回覆／完成）由 `todoStatus(t)` 推導：

```
done:true            → 'done'
status 是三個合法值   → 照用
都不是（舊資料）      → claimedBy 有人 ? 'doing' : 'open'
```

**舊待辦沒有 `status`／`progress` 也不會壞，不用轉檔**——推導那一行就是相容層。

`progress[]` 每筆：

| 欄位 | 型別 | 說明 |
|---|---|---|
| `id` | string | 同上 |
| `text` | string | 這次做了什麼 |
| `by` / `byName` | string | 誰寫的 |
| `at` | string | ISO |

狀態轉移（都在 `js/activity.js`）：

| 動作 | 結果 |
|---|---|
| 按「我來處理」 | 掛認領人，狀態一律 → `doing`（認領＝我在推它） |
| 再按一次放掉 | 清認領人；`waiting` 保持不動（卡在外部跟誰認領無關），其餘 → `open` |
| 加一筆進度 | `open` → `doing`；`waiting` 不動（那是刻意標的） |
| 按「等回覆」 | `waiting` ⇄ `doing`（toggle） |
| 打勾 | `done:true`，`status` 原封不動留著 |

⚠️ **待辦沒有像動態那樣的自動清理**（動態保留 60 天）。進度串是純附加，一則跑久了會一直長；量真的失控時要另外處理。

**新增走 `arrayUnion`**（原子加）；**認領／完成／刪除要改既有那筆，只能整份寫回** → 寫之前先重讀雲端最新的 `todos` 再套改動（`actTodoMutate`），把互蓋的窗口壓到最小。待辦是低頻操作，這個代價可接受。

### 讀取：onSnapshot 即時監聽（2026-08-03）

登入後 `watchActivity()` 掛上 `onSnapshot`，登出 `unwatchActivity()` 斷掉。**不走「切進分頁才重讀」**——待辦是三個人共用的，別人剛寫的那一行要自己浮出來。這份文件只有兩個陣列、很輕，長連線成本遠低於每次切分頁重抓。

- 監聽失敗（斷線／權限）→ 自動退回一次性 `loadActivity()`，畫面不會空著
- 雲端資料 → 本機狀態的轉換集中在 `actApplySnap()`，監聽與一次性讀取共用
- **過期清理一個 session 只做一次**（`actPruned`）——每次推播都清會白白多寫
- 本機 `logAct` 會先把新事件 push 進 `actEvents` 做樂觀更新，snapshot 回來時整份覆蓋成雲端真值（`arrayUnion` 對相同物件會去重，不會出現兩筆）
